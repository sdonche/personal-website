Five things the Ignition 8.3 SDK does not tell you.

2026-09-24 · 8 min read · Ignition

I spent a fortnight putting Doom inside an Ignition gateway. The joke is in its own note; this one is the bill. Building something deliberately useless turned out to be a thorough tour of the 8.3 module SDK, because the module ended up touching nearly all of it: a Perspective component with a gateway-side partner, a managed tag provider, a WebSocket servlet, HTTP routes with their own access control, per-user files in the data directory, signing, and an end-to-end test suite that boots a real gateway in Docker.

Five of those days went to things the documentation does not say. Here they are, so they cost you less.

1. A data route without access control never mounts

Module HTTP routes are built with a small fluent API, and it looks finished long before it is. Leave out the access control and mount() throws Access control must be specified — at gateway startup, into the log, where it reads as a single warning line: “Unable to mount routes for module”. The gateway keeps running. Everything else in your module works. The route is simply not there, and the browser gets a 404 that looks like a typo in your path.

The fix is one line, and the interesting part is that access control is a one-method interface, so a custom rule is a lambda. Mine admits a request that carries a ticket the component handed out over Perspective’s already-authenticated channel: 

routes.newRoute("/wads/:name")
      .method(HttpMethod.GET)
      .type(RouteGroup.TYPE_OCTET_STREAM)
      .accessControl(WAD_TICKET)   // leave this out and the route vanishes
      .handler(this::serveWad)
      .mount();

That pattern — the component asks the gateway for a short-lived ticket, then a plain HTTP or WebSocket request redeems it — is worth stealing. A page fetching a file over HTTP arrives with no session context. The ticket is how the session’s identity gets there.

2. WebSockets are allowed, and the Jetty version is yours to pin

A module can serve WebSockets: register a Jetty servlet through the gateway’s WebResourceManager and it answers under /system/<name>/. Nothing in the SDK hands you Jetty, though, so you declare the gateway’s exact version yourself as a compile-only dependency and never bundle it. Ignition 8.3.6 ships Jetty 12.0.27; when you bump the Ignition version you target, bump that line with it.

A sibling project that targets 8.3.1 had to unwrap Ignition’s request wrapper before Jetty would perform the upgrade. On 8.3.6 it just works. If you support both, expect that difference.

One free trick: a plain GET on the same servlet, with no upgrade, is a perfectly good status endpoint. Mine returns the live game rooms as JSON, which turned a debugging session from guesswork into a curl.

3. Perspective may hand a new view an old component’s store

This is the one that cost the most, and it is not a bug I can blame on anyone. Perspective recycles component stores. Open a different view whose component sits at the same address and it can be rendered once with the previous view’s props before the new view’s bindings apply.

For most components that window is invisible. For anything that acts on props at mount — starting an engine, opening a connection, writing a tag — it is a live grenade. My multiplayer test failed exactly one time in five: the component read its parameters, saw the schema defaults, and joined the wrong game before the bindings landed.

Two guards fixed it. First, when the view declares bound config props, wait for the first props update after mount, with a short settle timeout for bindings that resolve to the same value and therefore never fire. Do not gate on property qualities: a delivered binding may carry no quality entry at all, and you will wait forever. Second, remember the identity you started with and restart if a later update contradicts it — only when the props object itself changed, or your own state update will retrigger you.

4. The platform will not tell you its own version

There is no public API for the running Ignition version. I looked. The jars carry no manifest version either. What exists is the install’s own record, lib/install-info.txt, a plain properties file with a gateway.version key, sitting next to the data directory you can ask for. Your module’s own version, by contrast, is one call on the module manager.

The same theme runs through the small stuff. Gateway metric names are mostly unprefixed and hyphenated, and some contain spaces — log them, never guess them. In 8.3 scripting there is no system.tag.getHistorianProviders; you list historians by browsing system.tag.browseHistoricalTags(""). Saving a config resource whose content did not change fires no change event at all, so any hot-apply path that re-reads state from outside the resource has to re-apply explicitly, or the operator presses Save and nothing happens.

5. Build your native payload in a container, and have CI prove it

The engine is C compiled to WebAssembly. I committed the binary and moved on. Weeks later, rebuilding from the pinned sources in the pinned Docker image produced a game that showed a deathmatch frag counter in single player and ignored the turn keys.

The cause was a type. The engine defines its own boolean as a one-byte bool in files that have seen <stdbool.h> and as a four-byte enum everywhere else. Emscripten’s own headers include <stdbool.h>, so under the toolchain’s default C dialect the two halves of the program disagreed about the size of a shared global, and arrays of player state decoded as garbage. A local build with a newer compiler default hid it completely — which is why the committed binary worked and was never reproducible.

The lesson generalises past Doom: if you ship a compiled artefact inside a module, build it in one pinned container, commit exactly what that container produces, and have CI rebuild it and fail on a single differing byte. That job now runs weekly on the repo and takes ten minutes. It would have saved me two days.

Why write a useless module at all

Because the useless one is where you can afford to read the SDK properly. Nobody is waiting for it, so you follow the interesting path instead of the quick one, and you end up with working examples of the pieces that are genuinely hard to find: a component with a gateway-side delegate, a provider that creates its own tags, a WebSocket relay between browser sessions, tickets for unauthenticated fetches, signing and unattended install for the test gateway.

All of it is open, GPL-2.0, and the long form of these notes lives next to the code in docs/ignition-8.3-sdk-notes.md, with file and class names so you can read the working version of each one.
